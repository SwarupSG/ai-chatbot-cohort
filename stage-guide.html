One chatbot grows a few lines at a time over eleven stages

This page is your worksheet. Each stage has the same six parts in the same order. They are the learning moment, the mental model, the lines to think about, the predict question, the investigate questions and the tests. They are the one thing the stage teaches, a picture of what the model receives, the new lines, and a question to answer before you run. Open the reveal only after you have written your prediction.

Every command is typed at the root of your repository, in a terminal whose prompt shows (.venv); a new terminal tab needs source .venv/bin/activate before its first python command. Type quit to end a loop. The three tests at the end of each stage are the same at every stage: the behaviour test, the memory test and the budget test. Tick them as you go; the ticks are kept in your browser.

  • The model receives only what is in the list.
  • The program keeps the list; the model keeps nothing.
  • The code reads the key from the environment file.

Stage 0 · Base · check.py

Your laptop, keys and accounts are ready

The learning moment

The key is not part of the program. The code reads it from one file, .env, at the root, and that file is never uploaded to GitHub.

The mental model

.env at the rootis read bycheck.py01_base/stage1.py02_web/stage8/app.pyapp.py

One file is used by every stage, because the library looks for .env in the script's folder and in every folder above it.

The lines to think about

# 5. The key. The code reads it from .env; it is never written in this file.
key = os.getenv("LLM_API_KEY", "")
if not key or key.startswith("paste-"):
    print("LLM_API_KEY is not set yet. You will paste it into .env in the session. Nothing else to do now.")
    sys.exit()

Predict, then run

Now that your key is in .env, which line will python check.py print last?

What you should see

"Your laptop is ready. Models available: models/gemini-3.5-flash-lite, ..." The names carry a models/ prefix; the name written into .env is the part after the slash.

If the last line is a different one, read it: it says what to fix and which command to run again.

Investigate

  1. Which line reads the key, and which file holds it?
  2. Open .gitignore. Which line keeps .env out of GitHub?

Stage 1 · Base · 01_base/stage1.py

One call returns one reply that differs on every run

The learning moment

The model chooses among likely next tokens, so the same question gives a different answer each run, even at temperature zero. A token is a piece of text the model reads and writes; the provider counts tokens and charges for them.

The mental model

user: Suggest one name…the whole list is sent tothe modelwhich returnsone reply

The list has one entry. The model receives only what is in the list.

The lines to think about

# 2. Build the list. The model receives only what is in this list.
messages = [
    {"role": "user", "content": "Suggest one name for a small café by the sea ..."},
]
# 3. Call the model
response = client.chat.completions.create(
    model=os.getenv("LLM_MODEL"),
    messages=messages,
    # temperature=0,   # remove the # to make replies more similar
)

Predict, then run

Will a second run print exactly the same reply as the first?

What you should see

Two different names. With the temperature line uncommented, two runs are usually similar, sometimes identical, and never guaranteed identical, because the provider's hardware batches your request with other people's.

Investigate

  1. Which line would you change to ask a different question?
  2. What did run 2 send to the model that run 1 did not?

Stage 2 · Base · 01_base/stage2.py

The system entry is the first item in the list and it is code

The learning moment

The assistant's personality is text sent with every call: who it is, the facts it may use, and its rules. The model knows about the café only what the entry says.

The mental model

system: café facts and two rulesuser: questionboth are sent tothe model

Three questions make three separate calls, and the system entry is first in each. The system entry is first every time.

The lines to think about

# NEW in stage 2
system_entry = {"role": "system", "content": "You are the assistant of a small café ... Rule 1 ... Rule 2 ..."}
TEST_QUESTIONS = [
    "What time do you open on Sundays?",
    "What is the capital of France?",
    "Tell me everything about your menu.",
]
for question in TEST_QUESTIONS:
    messages = [system_entry, {"role": "user", "content": question}]

Predict, then run

What will the reply to "What is the capital of France?" do?

What you should see

The refusal sentence: "I can only help with questions about the café." The first question is answered from the facts, and the third in at most two sentences. A broken rule is possible: a rule is an instruction, and the test is what catches it.

Investigate

  1. Run it again. Do the words differ? Do the ticks differ?
  2. Which entry would you remove to make the model forget it works for a café?
  3. Change rule 1 to "answer in exactly one sentence" and run again. Which replies changed?

Stage 3 · Base · 01_base/stage3.py

A loop without memory forgets the previous turn

The learning moment

The model has nothing to forget, because it never stored turn 1. Each call is complete in itself, and what the program does not send, the model has not seen.

The mental model

systemuser: turn 1user: turn 2go tothe model

On turn 2 the list is built again. Turn 1 is in no list and no variable.

The lines to think about

while True:
    question = input("You: ")
    if question == "quit":
        break
    # 4. Build the list again every turn, so turn 1 is gone on turn 2.
    messages = [system_entry, {"role": "user", "content": question}]

Predict, then run

Turn 1: "I plan to visit on Sunday with two friends. Do you serve tea?" Turn 2: "Will you be open on the day I mentioned?" What will the model say to turn 2?

What you should see

The model asks which day, gives the opening times for every day, or gives the refusal sentence. All three are the same failure: the reply does not name Sunday, because turn 1 is not in the list on turn 2. This is the designed failure.

Investigate

  1. Draw the list the program sent on turn 2: one box per entry, with its role.
  2. Where in the code is turn 1 after turn 2 begins?
  3. Write one line: what would you add so that the model sees turn 1 on turn 2?

Stage 4 · Base · 01_base/stage4.py

The messages list is the memory, and the program sends all of it every time

The learning moment

The chatbot remembers because the program appends every turn and every reply to one list and sends the whole list on every call. The model still keeps nothing.

The mental model

systemuser 1assistant 1user 2assistant 2user 3all six are sent tothe model

The list is created once, before the loop, and grows by two entries per turn. The program keeps it; the model keeps nothing.

The lines to think about

# 3. Create the list once, outside the loop. This list is the memory.
history = [system_entry]
while True:
    ...
    # 4. The typed turn joins the list.
    history.append({"role": "user", "content": question})
    # 5. Send the whole list, every time.
    response = client.chat.completions.create(
        model=os.getenv("LLM_MODEL"),
        messages=history,
    )
    # 6. The reply joins the list too; print it with the number of tokens sent.
    reply = response.choices[0].message.content
    history.append({"role": "assistant", "content": reply})
    tokens = response.usage.prompt_tokens if response.usage else "unknown"
    print("tokens sent:", tokens)

Predict, then run

Turn 3: "How many cups of tea will we need for all of us on that day?" Will the reply refer to the Sunday visit or the group of three? Will the tokens number on turn 3 be bigger than on turn 1?

What you should see

Turn 2 names Sunday. Turn 3 refers to the Sunday visit or to your group of three. The tokens number grows every turn, from about 105 to about 200, because the whole list, replies included, is sent each time. Do not test memory with "what was my last question?": that question is not about the café, so rule 2 refuses it even though the list was sent. The three fixed turns ask about the café in a way that only turn 1 can answer.

Investigate

  1. You typed one short line on turn 3. Why did the number grow by so much?
  2. What is the largest the number could become?
  3. Three broken variants: the list created inside the loop; the reply never appended; the call sends only the latest turn. For each, which entries reach the model on turn 3, which test turn fails, and which printed number reveals it?

Stage 5 · Base · 01_base/stage5.py

The history has a token budget, and trimming keeps it inside

The learning moment

Every chatbot trims its history at some point: where its author set a limit, or where the context window ends. The list has a largest size, the context window, and a cost, the tokens sent.

The mental model

system, always keptuser 1assistant 1user 2assistant 2user 3three are sent tothe model

At KEEP = 2, the last two entries follow the system entry. The oldest turns are dropped first.

The lines to think about

# 3. ... set how many recent entries are kept. Two entries make one turn.
KEEP = 2
    ...
    history.append({"role": "user", "content": question})
    # 4. ... the list is trimmed. The system entry is always kept.
    if len(history) > KEEP + 1:
        history = [history[0]] + history[-KEEP:]

Predict, then run

KEEP is 2, which is one turn. Which memory test turn fails first?

What you should see

Turn 2 fails: turn 1 was dropped before turn 2 was sent. Sometimes Sunday is still in the list because the first reply repeated it; a fact remains after trimming only when a later entry repeated it. Set KEEP to 6 and every turn passes, at the highest tokens number.

Investigate

  1. Which entry is never dropped, and why?
  2. Write one sentence: which KEEP would you choose for the café's deployed chatbot, naming what it must remember and what it costs?

The tests

Stage 6 · Base · .env only

The provider is three environment variables

The learning moment

Nothing in the code names the provider. Changing three values in .env is all that a change of provider needs.

The mental model

LLM_BASE_URLLLM_API_KEYLLM_MODELare read by the same two client lines in01_base/stage5.py, unchanged

Put a # in front of the Gemini block, remove it from the OpenRouter block, and run the same script.

The lines to think about

# LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
# LLM_API_KEY=paste-your-gemini-key-here
# LLM_MODEL=gemini-3.5-flash-lite
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=paste-your-openrouter-key-here
LLM_MODEL=paste-a-model-name-ending-in-:free

Predict, then run

Which of the three tests will give a different result on the free model: behaviour, memory, budget, or none?

What you should see

The same three tests run, often with the same ticks. The tone and the speed may differ, the refusal rule may be weaker on a small model, and the tokens number may print as unknown. Free models allow about 20 requests a minute and 50 a day, are replaced without notice, and some may use your prompts for training. Do not type personal or client information into a free model. When the three tests are done, put the # back in front of the OpenRouter block and remove it from the Gemini block. Stages 7 to 9 then run on Gemini.

Investigate

  1. Which lines of the program changed? Write the number.
  2. For an application of your own, which provider would you choose, and what would change your mind?

Stage 7 · Web interface · 02_web/stage7/app.py, and test_chat.py at the root

A web route answers one chat request

The learning moment

The server does not remember the conversation. Each request carries its own list, which is why many people can use one server without their conversations mixing.

The mental model

1. the page or test_chat.py sends the listto2. the route function POST /chatwhich3. calls the modeland4. returns one replywhich5. the page shows

One cycle of five steps, the same for the test client, the page and a visitor on Vercel. GET asks for a page; POST sends data. The server keeps nothing between two cycles.

The lines to think about

# 4. The chat route: the caller's list arrives in the request body.
@app.post("/chat")
def chat():
    history = request.get_json()["history"]
    # 5. Add the system entry and trim. The caller never holds the system entry.
    messages = [system_entry] + history[-KEEP:]
    response = client.chat.completions.create(
        model=os.getenv("LLM_MODEL"),
        messages=messages,
    )
    # 7. Return one reply and the number of tokens sent. The server keeps nothing.
    return {"reply": reply, "tokens": tokens}

Predict, then run

Terminal 1: python 02_web/stage7/app.py. Terminal 2, also with (.venv) in the prompt: python test_chat.py. Will the memory test pass through the route, and what will the server's terminal show?

What you should see

Terminal 1 prints "Running on http://127.0.0.1:8000" and then one line per request, such as "POST /chat HTTP/1.1" 200. Read it as the method and the address, then the status number; 200 means the request went well. The WARNING line about a development server is printed on every start, and nothing is wrong when it appears. It says that Flask's own server is for one developer on one laptop; Vercel starts the application its own way. Terminal 2 prints the four turns with replies and tokens numbers; the memory test passes because the client resends the list. Stop the server with Ctrl+C, which the server itself names.

Investigate

  1. Where is the list between request 2 and request 3?
  2. What does the server keep between two requests?
  3. If all of you used one server at the same time, would your conversations mix?

Stage 8 · Web interface · 02_web/stage8/app.py and index.html

The page holds the history and the server holds nothing

The learning moment

The page and the test client are the same program in two languages: an empty list, a post of the whole list, and two appends. Whatever the page stores or sends, any visitor can read.

The mental model

index.html: const history = []sends all of it toPOST /chat, unchangedandGET / sends the page

Refreshing the page runs its code again, so the array is created empty again.

The lines to think about

const history = [];   // the list; created empty every time the page loads
history.push({ role: "user", content: text });
const answer = await fetch("/chat", {   // the whole list goes to the server
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ history }),
}).then((response) => response.json());
history.push({ role: "assistant", content: answer.reply });

Predict, then run

Open http://localhost:8000, type the three memory turns, then refresh the page and type turn 2 again. What does the chatbot remember?

What you should see

Before the refresh, the memory test passes. After the refresh, the model cannot name Sunday: the array was created empty when the page loaded. Open the browser's developer tools (F12, or right-click and Inspect) and choose the Network tab. Send one turn, click the request named chat, and read its body: it is the whole list. In the server's terminal, the first visit also shows "GET /favicon.ico HTTP/1.1" 404: the browser asked for a tab icon, there is none, and 404 means not found. The page works without it.

Investigate

  1. How many entries did the last request carry?
  2. Where would you look to see everything a page sends to a server?
  3. What changed in app.py in this stage, and what did not?

Stage 9 · Deploy · app.py, index.html and test_chat.py at the root

Deploy to Vercel with the key in the environment and the link protected

The learning moment

Deploying changes no line of the code, but it changes who can open the chatbot. The key is entered in the host's settings, and a passphrase check is added to the route, because anyone who finds the link can open it.

The mental model

your GitHub repositoryis built byVercelwhich runs app.py withfour values from its settingsforany visitor with the passphrase

The key is in Vercel's settings and in your root .env. The code, the page and the repository do not contain it.

The lines to think about

    data = request.get_json()
    # 4b. The passphrase check. The passphrase is the fourth environment value.
    #     A missing value gets its own message, so that it is not read as a
    #     wrong passphrase.
    if not os.getenv("APP_PASSWORD"):
        reply = (
            "APP_PASSWORD is not set on this server. "
            + "Add it in .env on your laptop, "
            + "or in Environment Variables on Vercel."
        )
        return {"reply": reply, "tokens": "unknown"}, 401
    if data.get("passphrase") != os.getenv("APP_PASSWORD"):
        return {"reply": "The passphrase is wrong.", "tokens": "unknown"}, 401
    history = data["history"]

Predict, then run

Once the app is on Vercel, where is the key? What would happen if it were written in index.html?

What you should see

The key is in Vercel's environment settings. A key written in the page would be readable by any visitor through the browser's developer tools, so it would be a key given to everyone. The steps are in 03_deploy/README.md. Run locally once and check that git status does not list .env. Push, import the repository in Vercel, type the four values into Environment Variables, deploy, and open the link. Post the project's own link, in the form https://<project-name>.vercel.app; the longer link with random letters is one deployment only. If APP_PASSWORD is missing on Vercel, the first reply says so. If the page itself says "This page is unavailable" with FUNCTION_INVOCATION_FAILED, one of the three LLM values is missing; the fix table in 03_deploy/README.md covers each case.

Investigate

  1. Who can use your chatbot now, and who pays for the tokens?
  2. What does the passphrase prevent, and what does it not?
  3. Why is the first request after a pause slower?

Stage 10 · Customise · 04_customise/MODIFY.md

Make it yours: change the persona, the model and the page, then redeploy

The learning moment

A chat application is three changeable things, the system entry, the page and the provider values, around a loop that never changes. Knowing which is which is what makes the code reusable.

The mental model

FileLines to changeLines to keep
app.pythe system entry; the KEEP numberthe client lines, the chat route, the trim line, the passphrase check
index.htmlthe title, the greeting, the stylethe array, the post, the two appends, the passphrase prompt
.env and Vercel's settingsthe provider's three values; the passphrasethe names of the four values
test_chat.pythe turnsthe loop, the post, the appends

The work

  1. In app.py, rewrite the system entry for a purpose of your own: who the assistant is, the facts it may use, and two rules.
  2. In index.html, change the title and the greeting.
  3. In test_chat.py, write your own three memory turns: a fact in turn 1, and a question in turn 3 that needs that fact.
  4. Run locally once, then commit and push.
  5. In Vercel, open Settings, then Environment Variables, and change the three LLM values to your OpenRouter block with a model name ending in :free. Press Save, then Redeploy from the Deployments page.
  6. Post your link and a note of three sentences: what you changed, what you kept, and why the kept lines must not change.

Predict, then run

To change the model on your deployed chatbot, which file do you edit?

What you should see

You edit neither app.py nor index.html. The provider is three values in Vercel's settings, and the deployed app changes after Redeploy without a push. That is stage 6's lesson applied to a deployed app.
